# データの扱い

このキットはエージェントが何をしたかを記録する。その記録は性質上、その機械を使う人の
個人情報になる。ホームのパス、プロジェクト名、ファイル名の中の顧客名。だから「できるだけ
少なく、できるだけ短く、自分が管理する1か所にだけ」を設計の前提にしている。

法的助言ではない。組織で使うなら、この内容が義務を満たすかは個人情報保護の担当が決める。
ここに書いてあるのは、その判断ができるようにするための材料。

## ディスクに残る物

- `state/exec-YYYYMM.tsv`：時刻、セッションハッシュ、ツール名、コマンド先頭240字（`0700`/`0600`）
- `state/egress-YYYYMMDD.txt`：既定経路、外向き接続とプロセス名
- `state/seen-callids.txt`：既に数えた呼び出しのハッシュだけ（中身は無い）
- `state/logs/exec-audit.log`：時刻と件数のみ。コマンド文字列は書かない
- `quarantine/<日付>/raw/...`：取得した原本（読取専用）、`text/...`：テキスト化した物、
  `manifest.tsv`：sha256・サイズ・MIME・取得元

## やらないこと

- **テレメトリ無し**。解析も更新確認も外部送信も無い
- **勝手な外向き接続は無い**。`ingest-quarantine.sh <URL>` で指定した取得だけ。`--verify`は
  設定した探査URLへ1回だけ`curl`する
- **クラウドもアカウントも無い**。全部ローカルのファイル
- **秘密の収集はしない**。キーチェーンも環境ダンプもブラウザプロファイルも読まない

## 書き込む前の最小化

マスクは後処理ではなく、書く前にやる。

- ホーム配下は`~`
- メール → `[email]`、電話らしい9桁以上の数字列 → `[num]`、UUID → `[uuid]`、長い16進 → `[hex]`
- `REDACT_TERMS`（カンマ区切り：人名・学校・取引先）→ `[redacted]`

```bash
REDACT_TERMS="acme,smith,kids" ./scripts/exec-audit.sh
```

限界も書いておく。`project/佐賀 中間テスト/`が個人情報だとツールは判断できない。自分で語を
登録するか、そういう物が載っている機械では監査を切る。実ログに対する最初の実行では、自分の
コマンド6件が引っかかり、どれも重要でなかった。パターンも語リストも生活に合わせて調整する物。

## 保持と削除

- 監査記録：**既定90日**（`RETENTION_DAYS=90`）。実行のたびに期限切れを消す。`0`で無期限
- 隔離した物：**自動削除しない**。`--purge-older 365`で1年より古い日を、`--purge`で全部を消す。
  どちらも明示の操作（隔離物は証拠になり得るため）
- 全部まとめて消すなら `exec-audit.sh --purge`

## アクセス

ディレクトリは`0700`、ファイルは`0600`。共有の機械ではそこが境界。暗号化は足していない。
ディスクが暗号化されていなければ（FileVault・LUKS）、記録はディスクと同じ強度でしか守られない。

## 制度との対応（設計上の当て）

- **利用目的の特定（個人情報保護法）**：目的は1つ「エージェントが何を実行したか」。READMEに明記
- **最小必要（PIPL）**：書く前にマスク、240字に切る、ファイルの中身は取らずコマンド行だけ
- **保存期間の制限（GDPR 5条）**：既定90日、自動失効
- **削除請求（APPI・PIPL・PIPA・GDPR）**：`--purge`の1コマンド。窓口も起票も要らない
- **越境移転なし**：外部に出ないので移転の告知が要らない
- **破棄（PIPA）**：プログラムで確実に消す。口約束にしない
- **安全管理措置（GDPR 32条）**：`0700`/`0600`、待ち受け無し、監査スクリプト自体のハッシュで
  改変が見える

DPIAや処理活動の記録が要る制度なら、上の表がそのまま棚卸しになる。

## 居心地の悪い話

実行ログは、その機械を使う人（共有なら複数人）の監視記録でもある。

1. 機械の中に置き、短く保ち、存在を口に出す。隠した監査ログは別の製品で、倫理も別
2. ログ自体が漏えい元にならないように。だから書く前にマスクし、既定の保持は年ではなく月
